# E4 · 多副本水平扩展（3×910B2 单卡副本 + nginx least_conn）

## 架构

```
            D 机（客户端 + LB，无数据面角色冲突）
   ┌─────────────────────────────────────────────┐
   │ vllm bench ─→ nginx :8080 (least_conn)       │
   │       ├─ :8001 ─ SSH隧道 ─→ M3 vLLM (910B2)  │
   │       ├─ :8002 ─ SSH隧道 ─→ M2 vLLM (910B2)  │
   │       └─ :8010 ─→ D 本机 vLLM (910B2)        │
   └─────────────────────────────────────────────┘
```

容器间无直连内网 → 用 SSH 隧道把各副本拉到 LB 同机 localhost，
nginx upstream 只配 127.0.0.1 条目；扩副本 = 加隧道 + 加 upstream + reload。
模型：全部副本 Qwen3.5-4B bf16 同权重。负载：random 512in/128out。

## 实测（干净轮，2026-11-05）

| 副本数 | c=32 吞吐 | c=128 吞吐 | c=128 TTFT | c=128 TPOT | c=128 扩展效率 |
|---|---|---|---|---|---|
| 1 | 565 tok/s | 1027 tok/s | 2751ms | 98.5ms | 1.00 |
| 2 | 837 tok/s | 1674 tok/s | 1494ms | 57.6ms | **1.63×** |
| 3 | 837 tok/s | **2160 tok/s** | 1262ms | 44.8ms | **2.10×** |

原始数据：`e4_n{1,2,3}_c{32,128}.json`；污染轮对照：`run1_e4_n*.json`

## 解读

1. **c=128 下吞吐 1027→1674→2160，效率 1.63×/2.10×（理想 2×/3×）**。
   亚线性来源：SSH 隧道每副本一条 TCP 流（多路复用上限）、least_conn
   按连接数而非 token 速率均衡、单机间 NPU 时钟差异
2. **c=32 时 N=2→3 不再增益（837→837）**：每副本仅 ~16 并发，低于
   饱和点（单副本 c=32 已 565，离 c=128 的 1027 还有距离）——副本收益
   只在"单副本被打满"后才兑现。**扩容时机要看单节点水位，不是越多越好**
3. **TTFT 随副本数下降**（2751→1494→1262ms）：队列等待被分摊，
   扩展对延迟的改善先于对吞吐的改善——低延迟 SLA 场景扩容收益更大
4. 副本一致性前提：同模型同权重同 max-model-len；least_conn 适合
   推理这种请求耗时不均的场景（轮询会把长请求堆到同一后端）

## 踩坑（这轮全是运维课）

| 坑 | 表现 | 解法 |
|---|---|---|
| bench 客户端与模型拷贝争 CPU | 第一轮数据 330/833 tok/s 异常低，N=3"诡异反超" | 拷贝结束重测；客户端必须闲 |
| 双 driver 并发 | 两套 nginx upstream/隧道互相重建，流量被打散 | 起后台 driver 前先查同类进程 |
| `nohup cmd &` 经 ssh 起隧道 | 会话关闭隧道被杀 → LB 502 | `setsid ... </dev/null` 脱离进程组 |
| 远端启动 nginx 挂住 ssh | daemon 继承会话 stdout，ssh 永不返回 | `setsid nginx </dev/null >/dev/null 2>&1` |
| pgrep self-match ×4 | kill 循环杀掉发起者自身（本地/远端/探针三种形态） | 模式加锚点 `^ssh`、`bin[/]vllm` 断字面量，或按 PID 杀 |

## E4b · 第四副本补测（M1 加入 upstream）

- 拓扑：D:8001→M3、8002→M2、8010 本机、**8003→M1**（新增 SSH 隧道 +
  nginx upstream server 127.0.0.1:8003）
- M1 用同一 `/model/Qwen3.5-4B` bf16 权重、`--max-model-len 8192`
- 注意：测量期间 M1 主机 CPU 上并行跑着 E6 的 bf16-27B PPL 评测
  （~10/192 核），M1 副本贡献可能被低估
- 踩坑：`e4_cluster.sh` step1 的 ssh 远端把隧道用 setsid 起了之后
  **会话通道仍不关闭**（OpenSSH 等 grandchildren 的 channel fd）→
  driver 卡死在 step2 前。杀该 ssh 进程后正常。教训：远端 daemon 化后
  仍可能挂住会话，编排脚本要给 ssh 加超时

| N | c32 TTFT | c32 TPOT | c32 输出 tok/s | c128 TTFT | c128 TPOT | c128 输出 tok/s |
|---|---|---|---|---|---|---|
| 1 | 645 | 49.2 | 565 | 2751 | 98.5 | 1027 |
| 2 | 448 | 32.2 | 837 | 1494 | 57.6 | 1674 |
| 3 | 1209 | 27.1 | 837 | 1262 | 44.8 | 2160 |
| **4** | **412** | **24.0** | **1029** | **1074** | **40.9** | **2061** |

### 解读

1. **c128 吞吐到平台了**：N=3→4 不升反微降（2160→2061，-4.6%，
   噪声/M1 CPU 竞争量级）。但 **TTFT 1262→1074ms、TPOT 44.8→40.9ms
   全面改善**——副本侧供给已大于客户端注入能力，新增容量只体现为
   排队变少。**瓶颈从后端迁移到了负载注入层**（单 bench 客户端 +
   nginx + 4 条 SSH 隧道全挤在 D 一台机上）
2. **c32 反而增益最明显**：837→1029（+23%）、TTFT 1209→412ms——
   N=3 那轮的 1209ms 本身就异常（方差大），4 副本把单副本水位压到
   ~8 并发后延迟分布收敛
3. **面试话术**：水平扩展的收益曲线是"先扩吞吐、再扩延迟、最后
   平台"——N=1→3 主要换吞吐，N=3→4 只换延迟，再往上就得先扩
   客户端/LB。判断扩容是否有效，看单节点水位是否过饱和点，
   而不是看副本总数

原始数据：`e4_n4_c{32,128}.json`（驱动日志 `e4b_driver.log`）
