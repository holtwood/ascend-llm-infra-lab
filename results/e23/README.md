# E23 — 客户端数扫描 + 工具对照：推翻"注入端天花板"，抓到自己的测量伪影

> 追问链：**"扩容不涨你怎么定位瓶颈？"** → "凭什么说是注入端？" →
> "客户端到底卡在哪？" → "换个工具还是这个数吗？"
> 结论：**E4b 的 2100 tok/s"天花板"是 `vllm bench serve` 的工具伪影**。
> 同一集群同负载，`bench_openai` 单客户端 3632、双客户端 4371 tok/s。
> 4 副本真实上限 **~4.2–5.0k tok/s**；客户端 CPU 全程 <1 核，不是 CPU 瓶颈。

## 数据一：客户端数扫描（固定总并发，只变进程数）

聚合口径 = 总输出 token / 最大墙钟（不是各客户端 tok/s 相加）。

| 聚合并发 | 客户端数 | 聚合吞吐 | 墙钟 | 说明 |
|---|---|---|---|---|
| c128 | 1（D） | 3632 tok/s | 6.8s | 单进程 |
| c128 | 2（D+M3） | **4371** (+20%) | 5.6s | 加一个进程有效 |
| c128 | 4（全机） | 4365 | 5.6s | 与 2 进程持平 → 副本侧见顶 |
| c256 | 1（D） | **5002** | 9.3s | 单进程反而最快 |
| c256 | 2 | 4322 (−14%) | 11.4s | 加进程变慢 |
| c256 | 4 | 4226 (−15%) | 11.6s | 更慢 |

**客户端 CPU 占用**（`ps %cpu`，1.0 = 单核满载）：c128 单客户端均值 31.6%、
c256 单客户端 37.2%，四客户端各 5.7–20.4%——**注入进程从未 CPU 饱和**。

## 数据二：工具对照（决定性）

同一 nginx、同一 4 副本、同 c128/256 请求、同 in256/out96：

| 客户端工具 | 聚合吞吐 | 备注 |
|---|---|---|
| `vllm bench serve` | **2193 tok/s** | E4b 用的就是它；自报 Peak 5270 |
| `bench_openai.py` | **3632 tok/s** | 同机同刻另一实现 |

**1.66× 差异纯来自测量工具**：vllm-bench 的 mean 口径含 ramp-up/down、
且其内部调度开销更大。E4b 的 N=3→N=4"平台 2100"因此不是副本饱和，
而是**压测工具自己的天花板**。

## 机制解释

1. **为什么 c128 加进程有用、c256 反而变慢**：c256 时单进程已能灌满副本
   （5002 tok/s），多进程只增加连接竞争与跨机客户端-副本 CPU 争抢
   （4 客户端所在节点同时跑副本，Python GIL 进程与 vLLM 线程抢核）。
2. **为什么客户端不是 CPU 瓶颈**：aiohttp 异步 IO 在 <1 核内就能维持
   ~3600 tok/s 的请求节奏；瓶颈在连接调度与副本侧排队，不在 Python。
3. **测量伪影的机理**：不同工具的"吞吐"口径不同——均值含 ramp 段、
   peak 只取稳态窗口。E4b 报的是均值，因此系统被低估约 40%。

## 对既有结论的修正（重要）

- **E4b**："N=4 吞吐平台 2100、瓶颈移到注入层" → 修正为：
  2100 是 `vllm bench serve` 的工具上限；4 副本真实上限 ~4.2–5.0k
- **E22**："4 客户端 +122%" → 相对基准应改用 `bench_openai` 单客户端
  （3632），则 4 副本的真实扩容收益为 **+20~38%**（4371/5002 对 3632）
- 保留成立的部分：**单客户端（vllm-bench）确实先撞墙**——这是"工具即瓶颈"
  的真实案例，适合讲"先验证测量工具，再下系统结论"

## 面试口径（三级追问都能接）

- Q: 扩容不涨怎么定位？→ 换注入源 + 换测量工具，两把尺子交叉验证
- Q: 客户端卡在哪？→ CPU <1 核，不是 CPU；是工具口径与连接调度
- Q: 你怎么知道之前错了？→ 同集群同负载两工具差 1.66×，我用第二个实现
  复现了第一个实现的天花板，因此判定为工具伪影——**主动修正自己的旧结论**
- 方法论：任何"系统上限"结论必须说明**测量工具 + 口径（均值/峰值）**

## 复现

```bash
# 客户端数扫描（自动采客户端 CPU%）
python3 scripts/e23_client_sweep.py
# 工具对照
vllm bench serve --base-url http://localhost:8080 --model qwen35-4b \
  --tokenizer /data/models/Qwen3.5-4B --dataset-name random \
  --random-input-len 256 --random-output-len 96 --num-prompts 256 \
  --max-concurrency 128 --ignore-eos      # → ~2193 tok/s
python3 scripts/bench_openai.py --base-url http://127.0.0.1:8080 \
  --concurrency 128 --num-requests 256 --input-tokens 256 --output-tokens 96
                                          # → ~3632 tok/s
```
