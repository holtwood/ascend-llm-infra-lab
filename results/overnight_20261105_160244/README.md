## E8i-ext：8×8 全对 p2p 矩阵（hccl_pairs.json）

56 个有向 pair × 5 种消息尺寸。结论：

| 尺寸 | 现象 | 数值 |
|---|---|---|
| 64MB | **全部 56 pair 均匀 19.7 GB/s** | 单链路饱和带宽 = 端口上限，与 pair 无关 |
| 1MB | 6.0–7.6 GB/s，pair 间 ±20% | 未饱和区暴露路径差异（如 1→0 = 7.6，2→1 = 5.6） |
| 1KB | 141–215 µs | 延迟底 ~150 µs，与 E8i 集合通信延迟底一致 |

**拓扑结论**：910B1 8 卡在饱和带宽下是**完全对称**的（无慢链路），
但中等消息有 ±20% 的路径不对称——TP 设计上**不需要 topology-aware 放置**，
但 1MB 级的通信（如 MoE all2all 小块）会吃到路径差异。

## E8k-ext：int8-KV 精度/成本网格（kv_quant_matrix.json）

32 配置：S∈{128..16384} × B∈{1..64}，GQA 广播实现（无 KV 展开）。

- **显存**：mem_ratio 恒 0.51（int8+bf16 scale ≈ 一半）——与 E8k 一致
- **精度随 S 收敛**：err_max 从 S=128 的 0.0117 降到 S=16384 的 0.0007
  （token 越多，量化噪声被平均得越充分）
- **naive 反量化税**：1.5–3.0×，且**不随 S 增大而下降**（长上下文里
  dequant 的元素级开销与 attention 计算同阶）——结论仍是必须融合 kernel

与 E8k（6.5–8.5×）的差异**已定位到代码级原因**（非猜测）：
E8k 的反量化是 `(q.float() * scale.float()).to(bf16)`——**float32 中间态**，
每个元素多一轮 fp32 读写的放大；本实验用 `q.to(bf16) * scale`（bf16 中间态）。
同一 S=8192 下两者 ref 相近（152µs vs 约 400µs/4batch），税差 2–4× 由此而来。

**结论更新**：naive 反量化的税不是单一数字，而是随中间态精度变化——
fp32 中间态 6.5–8.5×，bf16 中间态 1.6–3.0×。两者都必须融合进 kernel 才划算，
但引用数字时必须说明中间态精度，否则会差一个量级。

局限：本实验的 scale 是 per-token-per-head（`amax(dim=-1)`），不是真实 C8
KV 量化的 per-channel/per-block 方案；误差量级可作为上界参考。

## E8j-ext：paged gather 块粒度 + 页序对照（paged_gather.json / paged_gather_v2.json）

S∈{4096..32768} × block∈{16,32,64,128}，decode 形态（Sq=1，B=4）。
v2 增加**打乱页表（randperm）vs 顺序页表**对照：

| S | block | 顺序页 tax | 打乱页 tax |
|---|---|---|---|
| 4096 | 16 / 32 / 64 / 128 | 1.63 / 1.85 / 2.17 / 2.73 | 1.55 / 1.77 / 2.09 / 2.75 |
| 8192 | 16 / 32 / 64 / 128 | 2.15 / 2.11 / 2.22 / 2.42 | 2.15 / 2.11 / 2.29 / 2.42 |
| 16384 | 16 / 32 / 64 / 128 | 2.14 / 2.18 / 2.16 / 2.27 | 2.14 / 2.18 / 2.16 / 2.27 |
| 32768 | 16 / 32 / 64 / 128 | 2.13 / 2.15 / 2.14 / 2.12 | 2.13 / 2.11 / 2.13 / 2.13 |

**页序几乎无影响**（差 <0.1×）——advanced indexing 的拷贝量只由总字节决定。
所以本实验的 2.1–2.7× 与 E8j 的 3.3–15.6× 差异**不是页序造成的**，而是：

1. **页内布局**：E8j 的 pool 是 `[page, H, bs, D]`，gather 后还要 permute 成
   `[B,H,S,D]`（额外一次非连续变换）；本实验是 `[page, bs, H, D]`，gather
   后 view 即得 `[B,S,H,D]`，只需一次 transpose 视图
2. **GQA 实现**：E8j 用 repeat_interleave 把 KV 展开 4×（ref 更贵），本实验用
   batch 广播（ref 更便宜）——ref 越便宜，同样的 gather 成本对应税越高

结论不变（分页间接必须进 kernel），但**税的绝对值强烈依赖布局与实现选择**：
报告"分页税"必须同时报告页内布局和 GQA 实现方式，否则 2× 和 16× 都"对"。

## E8i-ext2：TP decode 步时实测（tp_decode.json，真 Qwen3-0.6B 权重）

单卡 8 卡独占，按行并行切分真实权重，decode 步（bs=1,seq=1）含每层 3 次
allreduce（qkv/o/down 后各一次；tp=8 时消息仅 256B，tp=2 时 1KB）。**两次独立运行**（含/不含
并发 soak）结果一致（差 <4%），下表为干净运行：

| TP | 步时 (µs) | 相对 tp=1 | 单次 allreduce | 通信占比 |
|---|---|---|---|---|
| 1 | 205 | 1.00× | — | 0% |
| 2 | 793 | **3.88×** | 185 µs | 70% |
| 4 | 842 | 4.11× | 206 µs | 73% |
| 8 | 915 | **4.47×** | 215 µs | 71% |

**结论**：0.6B 级模型的 decode 步，TP 的通信税**压过计算收益**——
8 卡比单卡慢 4.5×。步时构成：tp=8 总 915µs，其中单独测的 3 次 allreduce
约 645µs（70%），**剩余计算约 270µs，与单卡 205µs 同量级**——即切片并未
缩短计算（1×1024 的小张量 matvec 是延迟受限而非带宽受限，切分只增加启动开销）。
（注：allreduce 单独测量用 2KB 张量、真实步内是 256B，二者都在延迟平台区，
相减得到的"计算"只是量级参考，不是精确分解。）

另注：本模拟每层做 3 次 allreduce，真实 TP 模型通常 2 次（attention 后、
MLP 后各一次）——因此绝对步时会略高于真实实现，但 TP-vs-单卡的比值结论不受影响。

与 E8i（HCCL 原始延迟底 ~150µs）和 E8d（TP 通信税不随卡数降）完全自洽：
**小模型 decode 用副本不用 TP**，这是第三条独立证据链。

数据卫生：第一次运行时意外残留了一个 soak 进程（master 的 pkill 因 SSH
断连未生效），因此做了第二次干净运行；两者一致说明干扰 <4%，
但首轮数字不采用。

复现：`scripts/overnight/tasks/tp_decode_sim.py`（torch 级，不需要 vllm）。
