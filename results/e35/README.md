# E35 — Prefix cache 命中 → TTFT 收益曲线：命中约省 0.14s，但短前缀是负收益

> 面试题：**"prefix cache 能省多少？什么时候反而亏？"**
> 答：M3 同节点扫前缀长度，命中侧 TTFT 恒定 ~0.15s（与 P 无关——前缀被
> 跳过），未命中随 P 增长；**P≥1k 时命中省 ~0.14s（45-57%）**。
> 反直觉点：**256-token 前缀命中反而更慢**（0.163 vs 0.087s，−87%）——
> 查找/匹配开销超过重算成本，缓存不是免费的。

## 1. 方法

- 每个前缀长度 P：先 warm 一条共享前缀请求 → 6 条"同前缀 + 不同后缀"
  （命中侧）→ 6 条完全不同前缀（未命中侧），取中位
- TTFT 用 SSE 流式首 token 到达时间
- `enable_prefix_caching` 为引擎默认开启（启动日志确认）

## 2. 数据（M3 / Qwen3.5-4B）

| 前缀 P | 命中 TTFT med | 未命中 TTFT med | 节省 | 节省% |
|---|---|---|---|---|
| 256 | 0.163s | 0.087s | **−0.076s** | **−87.4%** |
| 1024 | 0.163s | 0.303s | +0.140s | +46.1% |
| 2048 | 0.102s | 0.236s | +0.134s | +56.6% |
| 3584 | 0.171s | 0.311s | +0.140s | +45.0% |

## 3. 机制解释

1. **命中侧 TTFT ≈ 常数**（0.10-0.17s，不随 P 涨）：前缀块命中后被跳过，
   只剩后缀 prefill + 一次调度步。这正是 APC 的设计收益。
2. **未命中侧随 P 增长**但非严格线性（1024 miss=0.303 > 2048 miss=0.236
   属运行噪声，±6% 波动常见）。
3. **节省平台在 ~0.14s**：因为单 token prefill 在这张卡上极快
   （4k ≈ 0.5s 总），省下的计算量换算成时间上限有限；
   真正的价值在**吞吐侧**——命中请求不占 prefill 预算，间接降低 E34 那种
   prefill stall 的概率。
4. **256 负收益**：P 太小，查找匹配（哈希/块遍历）+ 调度逻辑的固定开销
   超过重算 256 token 的成本——**缓存有盈亏平衡点**，本环境约在 256-1024
   token 之间。

## 4. 与 D3 拼成完整故事

- D3：prefix 亲和路由把命中率从 54% → 84%（路由层）
- E35：命中的价值 ≈ 0.14s/请求（P≥1k）+ 吞吐侧减负；但路由要保证的是
  **"长前缀命中"**——短前缀命中可能净亏
- 工程含义：路由策略可以按"前缀长度 × 命中价值"加权，而不是只看命中率

## 5. 局限

- reps=6、中位数；256 负收益是 6 次测量的中位但量级可能有噪声成分，
  复现时应加 reps 或用配对样本
- miss 侧 1024 vs 2048 顺序反常（0.303 vs 0.236），说明排队/调度噪声
  在 ±10% 级；趋势可信、单点精确值需谨慎
- 未测命中对**吞吐**的贡献（只测 TTFT）；多租户缓存驱逐下的收益衰减未测

## 6. 复现

```bash
python3 scripts/e35_prefix_cache.py --base-url http://127.0.0.1:8000 \
  --model qwen35-4b --prefix-sizes 256,1024,2048,3584 --reps 6 --out /tmp/e35.json
```
