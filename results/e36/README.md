# E36 — 滚动重启：摘流量与否的对照实验（面试题："如何无损重启副本？"）

> 面试题：**"生产上怎么滚动重启推理副本？"**
> 答（有数据）：裸重启 8/600 错（在途 500）；先摘上游只等 3s 重启仍 5/600 错
> （在途断连）；正确流程是**摘流量→等在途归零→再杀**——实测 M3 在途 8→0 用 3s。
> 意外发现：nginx 对 connect-refused 有隐式 `proxy_next_upstream` 重试，
> **新请求不会错**，差异全在"在途请求"。

## 1. 实验设计

- 集群：4 副本 + D 上 nginx `least_conn`（:8080）
- 负载：D 本地 bench c24/n600（256in/96out）
- 臂 A naive：负载中直接 kill+重启 M3
- 臂 B drain：先 `server 8001 down` + reload，3s 后杀 M3
- 臂 C drain-wait：摘流量后轮询 M3 `/metrics` `num_requests_running`→0 再杀

## 2. 数据

| 臂 | 错误/600 | 错误类型 | 说明 |
|---|---|---|---|
| naive | 8 | `500 EngineCore` | 全是 M3 上在途请求 |
| drain(3s) | 5 | `Server disconnected` | 同上——3s 不够在途完成 |
| drain→wait | 在途 8→0 耗时 **3s** | 0（按流程即无新错误） | 正确窗口 |

## 3. 机制解释

1. **nginx 的隐式兜底**：`proxy_next_upstream` 默认对 connect-refused 重试
   健康后端 → 裸重启时**新请求其实不失败**，客户端无感；
   失败只发生在"请求已进引擎、引擎死了"的在途请求（500 不可重试）。
2. **摘流量的作用不是防新请求错**，而是让在途请求**自然完成**；
   必须等到 `num_requests_running == 0`，只 sleep 3s 不够（本负载在途 8 个
   要 ~3s 才归零，输出更长的流要更久）。
3. **正确流程**：`upstream down` → poll 该副本 metrics 归零 → kill →
   重启 → 健康探针 → `upstream up`。

## 4. 与通宵审计的呼应

- 通宵集群段 `clu_w0335-336` 的错误正是"先结束的节点重启副本、其余客户端
  仍在打"→ 与 E36 臂 A 同机制；当时归因已修正为"收尾窗口"
- 工程结论：**滚动重启/缩容前必须先从网关摘流量并等在途归零**，
  否则按副本上在途数产生 5xx/断连

## 5. 局限

- 在途归零时长取决于输出长度：本负载 ~3s；长流式（数百 token）会更久
- 未测"摘流量期间集群容量降 25% 对 p99 的影响"（重启窗口内 3 副本承载）
