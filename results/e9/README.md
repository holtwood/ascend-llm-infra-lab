# E9 — Goodput@SLO：吞吐是虚荣指标，达标率才是容量

> 面试原题："throughput 和 goodput 有什么区别？SLO 怎么定容量？"
> 本实验用既有 bench 的 per-request 数据（ttfts/itls 数组）做二次分析，
> 展示**同一批测量在两种口径下给出完全不同的容量结论**。

## 方法

- SLO 判定（每请求）：`TTFT ≤ T` 且 `mean-ITL(TPOT) ≤ D`，取三档：
  `2000x100`（宽松）、`1000x100`（严格 TTFT）、`4000x150`（宽松 TPOT）
- goodput = 达标请求数 / 测试时长（rps）；与 `output_throughput`（tok/s）并列
- 脚本：`scripts/e9_goodput.py`，全量数据在 `goodput.json`

## 关键结果

### 1) 单副本并发扫描（E1，in~3500/out~200 sonnet）

| 并发 | 原始 out tok/s | 2000x100 达标率/goodput | 1000x100 达标率 |
|---|---|---|---|
| 1 | 75 | 100% / 0.57rps | 100% |
| 16 | 460 | 100% / 3.58rps | 100% |
| 32 | 651 | **100% / 5.02rps** | 87% |
| 64 | **807** | 88% / 5.52rps | **80%** |

→ 吞吐在 c64 最高，但**严格 SLO 下达标率已掉到 80%**。
容量结论完全不同：按吞吐你会报 c64，按 1000ms-TTFT SLO 只能报 c32。

### 2) 吞吐/goodput 极端分叉：w8a8-27B c64（E2）

| 配置 | out tok/s | 2000x100 | 1000x100 |
|---|---|---|---|
| w8a8-27b c64 | **396** | **7% / 0.23rps** | **5%** |
| w8a8-27b c32 | 312 | 54% / 1.3rps | 46% |
| w8a8-27b c8 | 149 | 100% / 1.17rps | 91% |

396 tok/s 的"吞吐"里 **93% 请求违反 SLO**——TTFT p99 达 7.2s。
裸吞吐把"排队等死"的流量也算成了产能。

### 3) 调度参数直接改写 SLO 画像（E3b，c32 长 prefill）

| mnb | out tok/s | 2000x100 达标率 |
|---|---|---|
| 256 | 162 | **2%** |
| 512 | 178 | 5% |
| 1024 | 221 | 12% |
| 2048 | 394 | 80% |
| 4096 | 470 | 84% |
| 8192 | 435 | 83% |

同一个 c32 负载，仅改 `max_num_batched_tokens`，SLO 达标率从 2%→84%。
**调参的价值要用 goodput 衡量**，裸吞吐(162→470)低估了整个数量级。

### 4) 副本扩容买的是 goodput（E4，c128）

| N | out tok/s | 2000x100 goodput | 4000x150 达标率 |
|---|---|---|---|
| 1 | 1027 | 34% / 2.7rps | 71% |
| 2 | 1674 | 70% / 9.0rps | 95% |
| 3 | 2160 | 74% / 12.4rps | 100% |
| 4 | 2061 | **85% / 13.5rps** | 100% |

注意 N=4 吞吐微降但 **goodput 反而最高**（13.5rps vs N=3 的 12.4）——
尾部延迟改善在吞吐口径里看不见，这正是"扩容收益要看 goodput"的证据。

## 机制解释（面试版）

- 吞吐统计所有产出 token，**不问等待**；SLO 把排队时间计入裁决。
  超 sat 点后新增并发只增加队列深度 → 吞吐平台 + goodput 崩塌。
- TTFT-SLO 对 prefill 排队最敏感（c64/mnb256/w8a8 大模型三个场景都在
  TTFT 上挂掉）；TPOT-SLO 对 decode 争抢敏感。
- goodput 曲线的峰值才是真正的服务容量；报告容量时必须附 SLO 定义。

## 注意

- `e3_spec_sonnet` 上 x100 TPOT 达标率仅 2% 是**指标假象**：spec decode
  每步产多 token，ITL 突发化，mean-ITL 不代表体验——spec 负载应改用
  e2e-latency 或 effective-TPOT 判定。指标选型本身也是考点。
- E8 压力数据（`results/e8/pressure_*.json`）无 itls 细节，未并入；
  其"准入受限"结论与本文 c64 达标率下降互为印证。
