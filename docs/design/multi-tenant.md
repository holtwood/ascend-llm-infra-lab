# 设计题：多租户/弹性 serving 怎么设计？

> 场景：一台 910B2 上要服务多个租户/多模型，怎么换租、怎么隔离、怎么保 SLO？
> 全部数字来自实测（E17/E20/E9/E8h）。

## 一、换租方案的实测成本表

| 方案 | 换租延迟 | 代价 | 实测 |
|---|---|---|---|
| 冷启新引擎 | **169.4s** | 权重加载+图捕获全量 | E17 |
| sleep→wake（CaMem） | **0.139s** | 睡眠期间占 ~3.5G 元数据+持 stream/CQ | E17 |
| 预热池（常驻 N 副本） | 0s | 每副本白占一份 KV 池 | E4 扩容账 |
| 权重 offload（不 sleep） | ~秒级 | 仅放权重，allocator/graph 还在 | E17 档 |

**关键不对称**：wake=0.14s 但首次冷启=169s——**sleep/wake 把弹性成本
降了三个数量级**，多租户设计的核心就是"把冷启挪出请求路径"。

## 二、隔离的真实坑（E17 签名坑）

- 睡眠引擎仍**持有 stream/CQ 资源** → 共卡新引擎只能 eager 起
  （EE1023/SQ-CQ 耗尽签名，我们 issue #21113 同根因）
- 换租窗口里第二引擎起服要 --enforce-eager + 控 gpu_memory_utilization
  （E-W8A16 实测：共卡 util 0.08 起 0.6B 到 warmup OOM 差 298MB）

## 三、SLO 保护：准入控制 > 排队

E20 实测的核心洞察：

- 排队把成本均摊给所有人 → 短请求 p90 被长请求拖死
- **快速 429 + retry_after** 把成本集中给后来者：short p90 4.85→3.10s（−36%），
  44/64 请求拿 <1ms 的明确拒绝信号
- goodput 口径（E9）：c64 吞吐最高时 93% 请求违反 SLO——**按 goodput 报容量，
  按吞吐报容量会虚高一个数量级**

## 四、推荐架构（答辩版）

```
接入层：分类器（短/长请求分道 E19-SRF 实测 short −7.2%）
  → 准入控制（per-class inflight cap，超限快速 429 + retry_after）
  → cache-aware 路由（D3 前缀亲和，命中 84% 但要做负载降级兜底）
资源层：活跃租户=常驻引擎；空闲租户=sleep（139ms 唤醒）
  → 新租户冷启走预热池遮蔽 169s
监控层：/metrics 盯 waiting_by_reason/kv_usage/preempt；
  输出质量抽检防 200-垃圾-token（E18 教训）
```

## 五、面试速答

> "多租户的核心是把冷启 169s 挪出请求路径——sleep/wake 实测唤醒 0.14s。
> 隔离上睡眠引擎仍持 stream/CQ，共卡要 eager 兜底。SLO 保护用准入控制
> 而非排队：实测快速 429 比排队让短请求 p90 好 36%。容量按 goodput 不按
> 吞吐报——同负载两种口径差一个数量级。"
